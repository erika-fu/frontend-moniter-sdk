Frontend SDK / Lesson 01

把一个仓库当成一组小项目管理

npm workspace 不是另一种包管理器，而是 npm 管理“同一仓库里多个 package”的能力。

先抓住一个画面

普通项目只有一个 package.json。当一个仓库同时包含 SDK、服务端、演示站和管理平台时，每个部分都需要自己的脚本和依赖，但它们又属于同一个工程。这时就可以让根目录成为“总项目”，让子目录成为 workspace。

frontend-moniter-sdk/
├── package.json       ← 总项目：登记 workspaces
├── demo/package.json  ← 一个 workspace
├── platform/          ← 一个 workspace
├── react-demo/        ← 一个 workspace
└── server/            ← 一个 workspace

在本仓库里找证据

根目录的 package.json 写着：

"workspaces": [
  "demo",
  "platform",
  "react-demo",
  "server"
]

这表示 npm 会把这四个目录识别为 workspace。根目录还提供了：

"dev:server": "npm --workspace server run dev"
"build:all": "npm run build && npm run build:server && ..."

第一条命令的意思是：“进入名为 server 的 workspace，执行它自己的 dev 脚本。”这里的 server 来自 server/package.json 的 name。

根项目负责统一安装、编排命令和共享工具链。
workspace仍是独立 package，有自己的依赖和 scripts。
npm --workspace把命令定向到某一个子 package。

它解决什么问题

没有 workspace 时，你可能要进入每个目录分别安装依赖、运行脚本，还要手动维护多个项目之间的一致性。使用 workspace 后，根目录可以统一执行：

npm install
npm run typecheck:all
npm run build:all

同时，子项目仍然可以单独运行：

npm run dev:server
npm run dev:platform
npm run dev:react-demo
别混淆：workspace 只解决“多个 package 如何组织和调度”。它不自动把所有源码打包成一个产物，也不等于 monorepo 工具；Lerna、Nx、Turborepo 等工具可以在 workspace 之上继续提供缓存、任务依赖和发布能力。
