Frontend SDK / Lesson 02

组织策略，还是包管理能力？

一句话：monorepo 是“怎么放代码”，workspaces 是“怎么管理这些包”。

先分清抽象层级

monorepo一种仓库策略：把多个项目或 package 放在同一个 Git 仓库中。
workspaces一种工具能力：让 npm、pnpm 或 Yarn 识别这些子 package，并统一安装和运行命令。

所以它们不是同义词。前者回答“代码放在哪里”，后者回答“包如何被管理”。

它们如何配合

一个 monorepo
├── packages/sdk
├── packages/ui
├── apps/demo
└── package.json
    └── workspaces: ["packages/*", "apps/*"]

上面整个目录是 monorepo；根目录的 workspaces 配置则告诉包管理器：这些目录是可管理的 workspace。

三种组合

最常见：monorepo + workspaces。比如本仓库把 SDK、服务端、Vue 演示、React 演示放在一起，并在根目录声明四个 workspace。

也可以只有 monorepo：多个项目放在一个仓库里，但没有统一的 workspace 配置，靠各目录自己的脚本和依赖管理。这仍是 monorepo，只是协作成本更高。

也可以把 workspace 理解为 package 管理范围：实际使用时它通常出现在 monorepo 中；但“workspace”这个词本身强调的是包管理器的工作区，而不是 Git 仓库策略。

补充：npm workspaces、Yarn workspaces、pnpm workspaces 是相似但不完全相同的实现。Nx、Turborepo、Lerna 等则通常提供任务编排、缓存、依赖图或发布能力，可以建立在 workspaces 之上。

和 polyrepo 对比

monorepo:  一个仓库 / 多个 package
polyrepo:  多个仓库 / 多个 package

选择 monorepo 往往是为了方便共享代码、统一变更和跨项目测试；代价是仓库规模、权限边界、构建速度和发布流程需要额外治理。

一分钟检验

判断：“只要使用了 npm workspaces，就一定是在使用 monorepo。”
